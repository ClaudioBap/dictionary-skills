# Boas práticas de Rust

⚠️ Esta secção não vem do PDF. Foi acrescentada a pedido do utilizador (2026-11-26), com o mesmo molde das outras linguagens: toolchain, estilo, estrutura, erros, testes, logging e segurança, lidos pela sub skill `boas-praticas-codigo` quando o projeto tem um `Cargo.toml`. Três entradas tratam do Rust na IA (servir modelos sem Python, acelerar código Python, chamar modelos e servir MCP) e são lidas também pela `ia-aplicada`; os ficheiros começam por `ia-`. O Rust é uma linguagem de uso geral; na IA usa-se onde o desempenho e um binário sem dependências contam.

Fonte: documentação oficial do Rust (The Book, Cargo Book, Edition Guide, API Guidelines, Clippy, rustfmt, Rustonomicon), RustSec e os repositórios oficiais de cada projeto, ligados em cada ponto; consultados a 2026-11-26. Não vem do PDF.

## Entradas

- [Concorrência e código assíncrono](concorrencia-e-assincrono.md) — O compilador só deixa passar dados entre threads quando os tipos são `Send` e `Sync`; o estado partilhado vai em `Arc<Mutex<T>>`. No código assíncrono, o Tokio é o runtime de referência, e o trabalho que bloqueia sai do runtime com `spawn_blocking` (curto), uma thread própria (longo) ou o rayon (CPU). *(fora do PDF)*
- [Erros com Result, ? e panic](erros-result-e-panic.md) — Uma função que pode falhar devolve `Result` e quem chama decide o que fazer; `panic!` fica para os bugs e para os estados que nunca deviam acontecer; `unwrap` e `expect` servem em exemplos, protótipos e testes; e os tipos de erro públicos implementam `std::error::Error`. *(fora do PDF)*
- [Estilo e formatação](estilo-e-formatacao.md) — O código formata-se com `cargo fmt` e revê-se com o Clippy, os dois no CI com os avisos a parar a compilação; os lints do projeto ficam em `[lints]` no `Cargo.toml`, e os nomes seguem o RFC 430 (UpperCamelCase para tipos e traits, snake_case para valores e funções). *(fora do PDF)*
- [Estrutura de projeto, crates e workspaces](estrutura-de-projeto-crates-e-workspaces.md) — Num binário, a lógica fica em `src/lib.rs` e o `main.rs` só a chama, para se poder testar; vários crates juntam-se num workspace com um só `Cargo.lock`; as features só acrescentam funcionalidade; e uma biblioteca pública passa pela lista das API Guidelines. *(fora do PDF)*
- [Chamar modelos e servir MCP a partir de Rust](ia-chamar-llms-e-mcp-em-rust.md) — Nem a Anthropic nem a OpenAI têm um SDK oficial em Rust: chama-se a API por HTTP ou usa-se um crate de terceiros, sabendo que o é. Para o MCP há SDK oficial em Rust, o `rmcp`, de nível 1. *(fora do PDF)*
- [Servir modelos de IA em Rust](ia-inferencia-em-rust.md) — Para correr um modelo sem Python há o candle (Hugging Face), o burn (Tracel), o mistral.rs (com um servidor compatível com a API da OpenAI) e o ort (ONNX Runtime, ainda em versão candidata). O Rust compensa quando se quer um binário leve, sem Python, para serverless, edge ou o browser (WASM). *(fora do PDF)*
- [Rust por baixo de Python (PyO3 e maturin)](ia-rust-a-acelerar-python.md) — Boa parte das bibliotecas de IA e dados que se usam em Python tem o núcleo em Rust (tokenizers, safetensors, pydantic-core, polars). O PyO3 liga o Rust ao Python e o maturin compila e publica as wheels; passa-se uma parte para Rust só depois de medir que é ali que o Python é lento. *(fora do PDF)*
- [Logging](logging.md) — O crate `log`, da própria rust-lang, é a fachada simples; o `tracing`, do projeto Tokio, junta eventos estruturados e spans e não obriga a usar o runtime. As bibliotecas emitem e a aplicação escolhe onde os registos vão parar, sem segredos nem dados pessoais. *(fora do PDF)*
- [Posse, empréstimos e desempenho](posse-e-codigo-idiomatico.md) — Cada valor tem um dono e é libertado quando o dono sai de âmbito; para usar um valor sem ficar com ele, empresta-se uma referência, em vez de o copiar com `clone`. O desempenho mede-se no perfil `release`, que já otimiza ao máximo mas não verifica o overflow de inteiros. *(fora do PDF)*
- [Segurança em Rust](seguranca-em-rust.md) — O Rust seguro não causa comportamento indefinido; o `unsafe` passa essa garantia para quem escreve, por isso cada bloco leva um `// SAFETY:` com a razão. O overflow de inteiros não dá erro em `release`, e as dependências auditam-se com o `cargo audit` contra a base do RustSec. *(fora do PDF)*
- [Testes](testes.md) — Os testes unitários ficam no próprio ficheiro, num módulo `#[cfg(test)]`; os de integração em `tests/`, onde cada ficheiro é um crate; e os exemplos da documentação também correm. Tudo corre com `cargo test`. *(fora do PDF)*
- [Toolchain, edições e dependências](toolchain-edicoes-e-dependencias.md) — Sai uma versão estável do Rust a cada 6 semanas (a 1.100.0 a 2026-11-12) e a edição atual é a 2024. O projeto fixa o toolchain em `rust-toolchain.toml`, declara o `rust-version` mínimo, guarda o `Cargo.lock` no controlo de versões e muda de edição com `cargo fix --edition`. *(fora do PDF)*
